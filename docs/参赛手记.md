# 参赛手记：把「AI 会说话」变成「AI 可以被校验」

> 魔搭 AI+∞ 第三期「AI 造游戏」· 故事与 AI NPC 赛道
> 线上：https://modelscope.cn/studios/mayi140611/lighthouse-seventh-night
> 源码：https://github.com/mayi140611/lighthouse-seventh-night

## 1. 为什么是「规则层」，而不是「更好的提示词」

最佳 AI NPC 奖有一条硬标准：**角色状态可量化、行为决策可由规则层校验、对话与行为闭环、开源**。

这条标准把大部分「AI 陪聊」挡在门外——它们能演，但你没法判断它为什么这么演。我们一开始也走错过：第一版想让模型自己维护信任值，结果同一个 NPC 在两轮里把「信任」从 60 改成 20，理由还说得通。演出是连贯的，状态是假的。

所以最终架构反过来：

```
玩家输入 → LLM 只输出 {reply, deltas, memory_writes, intent}
        → 契约校验（字段/范围/枚举）
        → 规则层钳制 + 阈值闸门 + 结局判定
        → 状态面板 / 记忆 / 下一轮
```

模型是「提案者」，不是「裁判」。它可以把台词演得很好，但数值怎么变、结局是什么，由一段可以单测的 Python 决定。

## 2. 三个具体的失败，和怎么改的

### 失败一：脚本 NPC 变成复读机

早期用确定性脚本跑离线演示，回复直接拼接玩家原话：「（他盯着海面，没接话。）面包给你，上船时带上我。」演示时像坏掉的客服。

改法：按意图分支给台词（威胁/试探/给物资/沉默），脚本只负责让四个结局可复现，不假装自己在聊天。

### 失败二：物资计数依赖模型写记忆

「已给出物资」一开始统计的是模型返回的 `memory_writes`。模型经常忘了写，于是玩家给了三次面包，面板还是 0，直接堵死「同舟」结局。

改法：**行为事实由规则层从玩家输入里判定**——面包/干柴/绷带各计一次，威胁不算。模型可以编台词，但不能决定「玩家到底给没给」。

### 失败三：线上卡在「加载中」

创空间部署成功、状态 Running，页面却一直转圈。根因是平台 Gradio 6.29.1，本地依赖装的是 5.x，前后端版本不匹配。日志里只有警告没有报错，很容易误判成网络问题。

改法：锁 `gradio==6.29.1`，把 `css/js` 移到 `launch()`，`Chatbot` 去掉旧参数，重新部署后正常。顺手把这条写进部署文档，避免下次再踩。

## 4. 可玩性是怎么被砍出来的

- **一局 12–18 分钟**：三个 NPC、四轮以上对话、四个结局；不追求时长，追求一局能讲完。
- **提示按钮**：给面包/提钥匙/问真相/威胁，降低第一分钟的理解成本。
- **规则层日志默认展开**：把「可校验」直接放在评委眼前，而不是藏在设置里。
- **二周目**：结局存档，重开时 NPC 记得上一局帮过谁，信任 +5。成本极低，传播点很强。

## 5. 已知不足

- **记忆引用的命中率还没量化**：现在面板只显示「记忆引用 N 次」，下一步会统计「主动提起且改变行为」的比例。
- **美术是剪影**：刻意避开 AI 味的写实脸，但也牺牲了表情；如果时间够，会做 2–3 张关键情绪立绘。
- **没有音效**：环境声（雨、浪、灯芯）能显著提升沉浸感，排在演示视频之后。
- **会话不持久**：创空间重启即清空存档，线上只做演示。

## 6. 如果再做一次

1. 先写状态机和结局判定表，再写任何台词——顺序反了会被模型带着走。
2. 给每个阈值写边界测试（我们 94 个用例里约一半是边界），否则调参时会悄悄改变结局可达性。
3. 把「线上版本」当独立交付物：本地能跑 ≠ 平台能跑，版本锁和部署文档要一开始就有。
